# Sybyl Standalone

Sybyl is a solo-TTRPG arbiter tool: a neutral, third-person-only assistant that tracks dice and scenes using the Lonelog notation. This repo is mid-migration from an Obsidian plugin to a standalone desktop app.

## Repo layout

- `app/` — the **standalone app**: Tauri + React + TypeScript + CodeMirror 6. This is where all active development happens. (The original Obsidian plugin this was ported from — `src/`, `main.js`, `manifest.json`, esbuild config, and its own README/TUTORIAL/USER_GUIDE/spec doc — was removed from the repo once the migration completed; see git history before this cleanup if you need it as a porting reference.)
- `docs/` — standalone reference docs:
  - `docs/BUILDING.md` — how to build/run the app for desktop, Android, and iOS, including every local-toolchain gotcha hit while setting up the release pipeline.
  - `docs/ROADMAP.md` — prioritized plan of future changes (tests/CI, external-change detection, prompt caching, streaming, play features, Android SAF).
  - `docs/lonelog.md` — spec doc for the Lonelog notation itself (parsing must stay 100% compatible with `app/src/lib/lonelog/`).
  - `docs/lonelog-dice-notation-addon.md`, `docs/lonelog-cards-addon.md` — formal grammar add-ons for dice expressions and card identities inside `d:` fields. Both are explicitly "grammar, not engine" specs (how to *write* notation, not how to resolve it) — see `app/src/lib/lonelog/diceNotation.ts`/`cardNotation.ts`.

## Standalone app architecture (`app/`)

- `app/src-tauri/` — Rust/Tauri shell. Plugins enabled: `fs`, `dialog`, `store`, `opener`.
- `app/src/lib/` — ported, provider-agnostic game logic (no React, no Tauri APIs except where noted):
  - `types.ts` — `NoteFrontMatter`, `SybylSettings`, provider configs. Extended from the original plugin with `pc_name`/`session_type` (standalone spec) and, as of Phase 4, the full Lonelog standard campaign-header field set from `lonelog.md` §5.1 (`title`, `player`, `start_date`, `last_update`, `tools`, `themes`, `notes` — `ruleset`/`genre`/`pcs`/`tone` already existed).
  - `promptBuilder.ts` — builds the system prompt + request from frontmatter and log body. Ported verbatim (Lonelog mode is always-on here, unlike the original plugin's optional mode). **Keep the system prompt byte-stable per note** (as of 2026-10-05 it's an Anthropic prompt-cache breakpoint, see `providers/anthropic.ts`). Nothing that changes between requests or on every save goes in it: no dates, and no PC state, which is why it uses `pcNames()` rather than raw `pcs`. Per-request material belongs in the user message. `promptBuilder.test.ts` asserts this.
  - `lonelog/parser.ts`, `lonelog/formatter.ts` — ported verbatim, zero changes.
  - `lonelog/diceNotation.ts`, `lonelog/cardNotation.ts` (Phase 5) — regex-based recognizers for the dice/card notation add-on grammars (`lonelog-dice-notation-addon.md`/`lonelog-cards-addon.md`), each exporting a global `*_TOKEN_REGEX` plus an anchored `is*(token)` check. Dice covers the addon's Part I practical subset only (not the full Part II grammar — no min/max, compounding/penetrating, reroll, unique, critical success/failure, sorting, group rolls, or full math with parens/exponents). Neither module rolls/draws anything — notation recognition only, no engine.
  - `toolkit/diceEngine.ts`, `toolkit/cardEngine.ts`, `toolkit/wordGenerators.ts`, `toolkit/tables.ts` (Phase 6), `toolkit/oracleEngine.ts` (Phase 7), `toolkit/customDeckEngine.ts`, `toolkit/cutup.ts` (Phase 8) — the actual solo-toolkit *engine* layer on top of Phase 5's grammar. `diceEngine.ts` executes exactly the Part I expression shape `diceNotation.ts` recognizes (own regex with named capture groups, not a reuse of the flat token regex) and formats results via the addon's `expr=total`/`expr=successes` convention. `cardEngine.ts` builds standard/tarot decks and produces tokens in `cardNotation.ts`'s exact shorthand, with a `DeckSession` draw/discard/reshuffle model (reversal for Tarot decided at draw time, not baked into the deck) — also exports `shuffle<T>()`, reused by `customDeckEngine.ts` and `cutup.ts`. `wordGenerators.ts` has 8 categories of original curated word lists (not ported from any external plugin). `tables.ts` reads user-authored plain-text tables (one entry per line, optional `^N` weight) from `<vault>/tables/`. `oracleEngine.ts` is a deterministic Yes/No oracle (likelihood 9-point scale × a 1-9 Chaos Factor dial → `askOracle()`/`formatOracleResult()`), with exceptional results and a random-event roll (`rollRandomEvent()`, an original event-focus table + `wordGenerators.ts`'s `noun` category as the "subject") — an **original probability formula**, not a port of any published product's fate-chart table (those exact numbers are proprietary; only the feature *shape* was consulted, same precedent as `wordGenerators.ts`). Distinct from `cmdAskOracle` in `App.tsx`, which is LLM-driven — this one never calls a provider. `customDeckEngine.ts` scans `<vault>/decks/<name>/` (same `exists()`-guarded, no-auto-create convention as `tables.ts`) for image files, builds a `CustomDeckSession` (parallel to `cardEngine.ts`'s `DeckSession` but over image paths, not text tokens, so deliberately not unified with it), and reads a drawn image into a `data:` URI (`imageToDataUri()`, reusing `arrayBufferToBase64` from `sourceUtils.ts`) for in-panel preview — no Tauri asset-protocol config, and draws are never inserted into a note (no Lonelog notation for an image). `cutup.ts` implements the Burroughs cut-up technique (`cutUpText(text, "words" | "lines")`) — shuffles a block of text's words (rewrapped every 8 per line) or lines; has no Lonelog spec basis either, so output is inserted as plain text like any other Toolkit result.
  - `lonelogHighlight.ts` — CM6 `MatchDecorator`/`ViewPlugin` extension (as of 2026-09-29 also a `lineClassPlugin` adding whole-line `cm-lonelog-line-scene`/`cm-lonelog-line-<beat>` classes, styled in `App.css` with the `--beat-*`/`--lonelog-scene` color tokens) highlighting scene headers, `[N:]`/`[L:]`/`[PC:]`/`[Thread:]`/`[Clock:]`/`[Track:]` tags, and beat-prefix lines (`@`, `?`, `d:`, `->`, `=>`). As of Phase 5, also a line-scoped `ViewPlugin` (not `MatchDecorator` — needs line-prefix awareness) that highlights dice/card tokens found on `d:`-prefixed lines only, using `diceNotation.ts`/`cardNotation.ts`. Layered on top of `markdown()`, not a replacement language.
  - `editorUtils.ts` — CM6 `EditorView` equivalents of the original plugin's `src/editor.ts` (Obsidian `Editor` API): `insertAtCursor`, `appendToNote`, `getSelection`, `insertBelowSelection`, `isInsideCodeBlock`, `wrapSelection`, `togglePrefixLine`, and (Phase 9) `insertFootnote` — auto-numbers a `[^n]` reference at the cursor and appends a matching `[^n]: ` definition stub at the document end in one transaction (two changes in one `ChangeSet`, both specified in original-document coordinates — no manual position remapping needed).
  - `providers/` — `anthropic.ts`, `openai.ts`, `gemini.ts`, `ollama.ts` + `base.ts`/`index.ts` factory. Same request/response shapes as the original plugin, with Obsidian's `requestUrl` swapped for `fetch`. **Anthropic requires the `anthropic-dangerous-direct-browser-access: true` header** since Tauri's webview enforces CORS like a real browser.
  - `vault.ts` — vault folder picker + persistence (`@tauri-apps/plugin-store`), list/read/write `.md` files via `gray-matter`. **Requires a `Buffer` polyfill** — see Gotchas below. As of the Android mobile-fixes pass, also exports `isAndroid()` (UA sniff) and `initAndroidVault()` — see Gotchas: `@tauri-apps/plugin-dialog`'s Android backend has no folder-picker implementation at all, so `pickVaultFolder()` can never resolve there; Android auto-initializes its vault in `appDataDir()/vault` instead, and `Sidebar.tsx` hides the "Change vault" button on Android accordingly. As of 2026-10-05 it also guards against outside edits (see Gotchas): `openVaultFile()` records a note's raw text as the baseline, and `writeVaultFile()` refuses with `ExternalChangeError` if the disk no longer matches unless `{ force: true }` is passed. App writes go through `writeGuarded()`, which opens `ConflictModal.tsx`.
  - `settings.ts` — default settings + normalization.

**Review/debug pass (2026-09-27)**, version bumped 0.14.0 → 0.14.1. Bugs found by reading the code and fixed:
- **Undo leaked across notes (data-corrupting)**: `Editor.tsx` synced an external `value` change (switching notes, restoring a snapshot) by *dispatching* a full-document replace. That went into CM6 undo history, so Ctrl+Z after opening note B restored note A's text into B, and autosave then persisted it. It also fired `onChange`, so merely opening a note re-saved it and bumped `last_update`. Now uses `view.setState(EditorState.create(...))` with the same extensions (kept in a ref), which resets history and doesn't fire update listeners.
- **Ctrl+I never italicized**: `basicSetup`'s `defaultKeymap` binds `Mod-i` to `selectParentSyntax` and came earlier in the extension array, so it won. The Bold/Italic/Code keymap is now wrapped in `Prec.high` (and the redundant `history()`/`defaultKeymap`/`historyKeymap` entries, already inside `basicSetup`, were removed).
- **Edits lost when switching notes within 500ms of typing**: the debounced save bailed out if the active note had changed. It's now `pendingSaveRef` + `flushPendingSave()` (flushed on note switch/vault change) + `discardPendingSave()` (on delete/restore, so a late write can't resurrect a deleted note or clobber a restore).
- **Generation output could land in the wrong note**: if the user switched notes mid-request, `insertFormatted` inserted into whichever note was then open. `executeGeneration`/`runRawGeneration` now check `stillActive(file)` after the await and discard with a status message. `runGeneration` returns a success boolean, and Start Scene only bumps `scene_counter` on success. Before this, a failed or cancelled call burned a scene number.
- **Status bar vanished mid-generation**: every `flashStatus` scheduled an un-cancelled clear, so an earlier "done." timer could blank "generating..." (and its Cancel button). Timer now lives in `statusTimer`, and `showStatus()` cancels it.
- **Android API keys never persisted**: the `keyring` crate has no Android backend (mock store), and `saveSettings` blanked keys from the settings store. On Android they now stay in the (app-private) store.
- **Provider API fixes**: OpenAI reasoning models (`gpt-5*`, `o1/o3/o4*`) now get `max_completion_tokens` (they reject `max_tokens`) and no temperature. OpenAI source text cap raised from 4000 to 200k chars (Digest Source used to see only a page or two). Gemini `thinkingBudget: 0` is now sent only for 2.5 Flash models, since 2.5 Pro and newer reject it.
- **Smaller fixes**: `normalizeSettings` merges per provider (a stored config missing a field no longer drops the default). Per-note `provider:`/`model:` frontmatter overrides now actually work (they were typed but ignored) and are documented in the User Guide. Ctrl+K no longer opens an inert palette with no note open. `ListPickerModal` autofocuses its first item. Selecting a note closes the mobile sidebar. The sidebar heading "Campagne in corso" became "Campaigns". Custom-deck image read errors are caught, and the custom deck session resets on vault change.
- Verified: `tsc --noEmit` and `npm run build` clean, then confirmed live by the user in `tauri dev`: no undo leak across notes, Ctrl+I italicizes, the palette filters, edits survive a fast note switch, and a mid-generation note switch discards the result. The Android API-key fix is still untested on a device.

## Status as of 2026-08-07

**Android mobile-testing fixes (2026-08-07)**: the repo's first real on-device Android build (via `docs/BUILDING.md`) surfaced four bugs, all fixed:
1. **Launcher icon was Tauri's default logo**, not Sybyl's — `tauri android init`/`ios init` scaffold the mobile project with Tauri's own default icon; only running `tauri icon src-tauri/icons/icon.png` afterward overwrites it with ours. Fixed locally and added as a step in both `release.yml` mobile jobs (after their respective `init` steps) and documented in `docs/BUILDING.md`.
2. **Command bar didn't adapt to narrow viewports** — `.command-bar`/`.command-bar-actions` had no wrap/shrink rules, so the 5 action buttons (with Ctrl+O/Ctrl+K keyboard hints, meaningless without a physical keyboard) overflowed. Fixed in `App.css`'s existing `@media (max-width: 720px)` block: `flex-wrap` on both, hidden `.kbd-hint`, smaller button padding/font, and `.active-file-name` dropped to its own wrapped row.
3. **Sidebar had no way to close once opened on mobile** — the off-canvas sidebar (Phase 10) covered its own hamburger toggle when open, with no other close affordance. Fixed by adding a `.sidebar-backdrop` (click to close) and a `.sidebar-close` × button in `Sidebar.tsx`'s header (both `display: none` outside the mobile breakpoint); `Sidebar` now takes an `onClose` prop.
4. **Vault picker didn't work on Android at all (critical)** — traced to `@tauri-apps/plugin-dialog` v2.7.2 (latest published version): its Android Kotlin backend (`DialogPlugin.kt`) implements only `showFilePicker`/`saveFileDialog`/message dialogs — **no folder-picker command exists on Android**, so `open({ directory: true })` can never resolve there. Rather than build a custom Storage-Access-Framework plugin (a multi-day native feature), the user chose the fast path: Android now auto-initializes its vault in `appDataDir()/vault` via `initAndroidVault()` (`vault.ts`), and `Sidebar.tsx` hides "Change vault" on Android (`isAndroid()` UA sniff) since there's nothing it could do. Desktop behavior (`pickVaultFolder()`) is untouched.

All four verified: 1 via direct pixel comparison of the regenerated `mipmap-xxxhdpi/ic_launcher.png`; 2-3 via a live `vite dev` pass in Chrome (the OS window had to be un-maximized via a Win32 `MoveWindow` call before `resize_window` would actually shrink the viewport — worth remembering if this comes up again) — DOM state confirmed via direct JS (`sidebar-open` class + backdrop appearing/disappearing on toggle/backdrop-click/×-click) plus a real narrow-width screenshot; 4 via reading the actual installed plugin's Kotlin source in the Cargo registry cache, since there's no on-device way to get a stack trace for a native command that doesn't exist. A full rebuilt + re-signed APK was produced (`app-universal-release-signed.apk`, same throwaway `sybyl-test.jks` from the first test build) but not yet installed on a device to confirm the vault fix end-to-end — no device was connected in that session.

**Post-Android bug reports and fixes (2026-08-07)**: further live use of the same build surfaced six more issues, all fixed same-session:
1. **Editor was always dark regardless of theme setting** — `Editor.tsx` applied CM6's `oneDark` unconditionally. Fixed by adding a `theme` prop and a hand-built `lightEditorTheme` (`EditorView.theme()`) for light mode, plus `:root[data-theme="light"] .cm-lonelog-*` overrides darkening the Lonelog syntax-highlight palette (tuned pastel-bright for dark backgrounds, illegible on light). First attempt used a shared module-level CM6 `Compartment` to hot-swap themes without remounting — this **broke dark mode** (partial styling, washed-out gutters) because a `Compartment` must stay bound to one `EditorView`'s lifecycle, and React Strict Mode's double-invoked effects in dev reused it across remounts. Fixed by just fully remounting the editor (`useEffect` keyed on `[theme]`) instead of reconfiguring a compartment — a scroll/cursor-position reset on the rare theme-toggle click is a fine trade for guaranteed-correct styling.
2. **Generate Character / Ask the Rules always required re-picking a raw source file**, even when `game_context` was already digested — defeating the entire point of Digest Source ("distilled once, reused on every request"). Both now check `fm.game_context` first and only fall back to requiring a source pick when nothing's been digested yet.
3. **`game_context`/`scene_context` were invisible** — `CampaignInfoPanel.tsx` never displayed them, so there was no way to confirm a digest actually landed. Added both as rows (later `scene_context` was removed entirely, see below).
4. **Digest Source was inventing rules instead of reading the source file (critical)** — `sourceUtils.ts`'s `resolveSourcesForRequest` routed **every** source through the PDF/base64 branch whenever the active provider was Anthropic, regardless of the file's actual type (`providerId === "anthropic" || ...`, no PDF check). `anthropic.ts`'s request builder only reads `base64Data` when `mime_type === "application/pdf"`, so a `.txt`/`.md` source under Anthropic ended up with neither `base64Data` nor `textContent` populated — silently dropped from the request entirely, with the model filling the gap from its own general knowledge. Fixed by gating the base64 path on `ref.mime_type === "application/pdf"` first, provider second. Audited Gemini/OpenAI/Ollama for the same class of bug — none had it.
5. **Settings model-picker "Refresh" appeared to do nothing** — `<input list>`/`<datalist>` works mechanically (confirmed by testing identical markup live), but WebView2 (what Tauri actually embeds on Windows) renders its dropdown affordance far less visibly than desktop Chrome. Replaced with an explicit `<select>` that appears once models are fetched (input stays for typing an unlisted model ID), plus a visible error message instead of silently swallowing fetch failures — confirmed live via a patched `window.fetch` returning fake models.
6. **`scene_context` frontmatter field / "Update Scene Context" command were dead weight** — `buildRequest` in `promptBuilder.ts` always passes the live editor body as `noteBody`, and since that's truthy for any real note, the `fm.scene_context` fallback branch was unreachable in practice; the command computed a value nothing ever read. Root cause: `CLAUDE.md`'s own porting notes confirm Lonelog mode used to be *optional* in the original Obsidian plugin (this standalone app made it always-on), and `scene_context` was almost certainly the freeform-note fallback for that now-gone branch. Removed entirely, per the user's call: the command, the frontmatter field/type, the promptBuilder fallback, and its README mentions.

Two smaller follow-up fixes in the same session: "Start Scene"/"Insert Scene Template" (renamed from "Insert Quick Scene" — not from the original plugin, it's the standalone port's Phase 5 implementation of `lonelog.md` §8.4's "Quick Scene Template," for manual/analog play with no AI call) had a mandatory "Scene description" field; "Declare Action" had a mandatory "Roll result" field. ## Gotchas specific to this codebase

- **`gray-matter` needs a `Buffer` polyfill.** It unconditionally calls `Buffer.isBuffer`/`Buffer.from`, which don't exist in the Tauri webview. `app/src/lib/vault.ts` imports the `buffer` npm package and assigns it to `globalThis.Buffer` before gray-matter is used. If file reads start silently failing (sidebar shows "no files" with no console error), check this first — errors here get swallowed by a per-file `try/catch` in `listVaultFiles`.
- **Streamed output in the editor is provisional, so read the note through `docWithoutLiveOutput`, never `view.state.doc.toString()`.** Since 2026-10-06, every `provider.generate()` streams (`providers/stream.ts`). `executeGeneration` writes the output into the editor as it arrives through `lib/liveOutput.ts`. Its span is tracked by the `liveSpanField` CM6 state field, its updates are dispatched with `addToHistory: false`, and the finished text is committed as one ordinary undoable insert. The pieces that keep half-finished output off disk all depend on that: `Editor.tsx`'s `onChange` and its value-sync check, and `App.tsx`'s `currentDoc()`. A raw `doc.toString()` would include the partial output, so autosave could persist it. In the value-sync case it's worse: typing during a stream would look like an external change, reset the editor, and kill the stream. Any new CM6 `EditorState.create` must include `liveSpanField`; `Editor.tsx` already does. Provider tests build streamed `Response`s with `src/test/stream.ts`, which splits chunks mid-event and mid-character on purpose. Ollama `qwen3.5:9b` on this machine runs at about 2 tokens/sec and thinks first, so live streaming tests against it need a tiny `num_predict`.
- **Note writes are guarded against outside edits. Don't bypass the guard and don't record baselines from list reads.** `vault.ts`'s `knownContent` map holds each note's raw text as of Sybyl's last `openVaultFile()` or write. Only those two set it. `listVaultFiles`/`readVaultFile` deliberately don't: the sidebar re-reads every note, and recording there would make a stale open editor look current, so its next autosave would overwrite the outside edit. Open a note for editing with `openVaultFile`, never by reusing the sidebar list's cached `VaultFile` (that copy is from the last list load). In `App.tsx`, write the active note through `writeGuarded()`, and put the new state in memory *before* the write (`applyFileState`). On a conflict, the in-memory state is the user's side, so a frontmatter patch such as a fresh `game_context` isn't lost. `{ force: true }` is only for brand-new paths (`createVaultFile`/`importNoteFile`) and the user's explicit "Keep my version". Writes to one path are queued (`writeQueue`): overlapping writes produced false conflicts, because a second write's check could read the first one's content off disk before `knownContent` caught up. `vault.test.ts` reproduces this only because its mock `writeTextFile` lands on disk *before* resolving, like the real IPC call. Keep that mock behavior.
- **`matter.stringify()` throws on `undefined` frontmatter values** (YAMLException). `vault.ts` filters them out via `withoutUndefined()` before serializing — don't remove that.
- **Local reasoning models (e.g. Ollama `qwen3.5:9b`) can return an empty response** if `maxOutputTokens` is too small — they spend tokens on hidden "thinking" before the visible answer. This surfaces as `Error: Provider returned an empty response.` It's a token-budget/model-choice issue, not a code defect.
- **MSVC Build Tools**: if `cargo build`/`tauri dev` can't find `cl.exe`, don't trust `vswhere -requires VC.Tools.x86.x64` alone — check for `cl.exe` directly under `...BuildTools\VC\Tools\MSVC\<version>\bin\Hostx64\x64`. The winget install of `Microsoft.VisualStudio.2022.BuildTools` can silently skip the actual compiler package even when the VCTools workload is requested; a follow-up `vs_installer.exe modify --add Microsoft.VisualStudio.Component.VC.Tools.x86.x64` fixes it.
- **`@tauri-apps/plugin-dialog` has no folder-picker on Android, at any version up to the latest published (2.7.2).** Its Android Kotlin backend (`DialogPlugin.kt`) only implements `showFilePicker`/`saveFileDialog`/message dialogs — no `ACTION_OPEN_DOCUMENT_TREE` command exists. Calling `open({ directory: true })` on Android has nothing to invoke; there's no error surfaced in JS beyond it just never resolving usefully. Don't try to "fix" this by tweaking capabilities/permissions — it's not a permissions issue, the native command genuinely doesn't exist. `vault.ts`'s `isAndroid()`/`initAndroidVault()` sidestep it entirely by auto-using `appDataDir()/vault` on Android instead of picking. Confirmed by reading the actual plugin source at `~/.cargo/registry/src/index.crates.io-*/tauri-plugin-dialog-<version>/android/src/main/java/DialogPlugin.kt` — the fastest way to check platform support for a Tauri plugin command is to read its real Android/iOS source directly rather than guess from the JS API surface, since the JS types don't reflect per-platform gaps.
- **Windows Developer Mode is required to build for Android on Windows.** Tauri's Android build symlinks the compiled `.so` into the generated Gradle project's `jniLibs` folder; creating symlinks on Windows needs Developer Mode (Settings → Privacy & security → For developers, or `start ms-settings:developers`). Without it, the Rust cross-compile succeeds for all 4 ABIs, then packaging fails at the very last step with "Creation symbolic link is not allowed for this system." See `docs/BUILDING.md` for the full local Android build setup.
- **The Chrome extension's `resize_window` tool doesn't shrink an OS-maximized window** — it silently no-ops (viewport stays at full screen size, confirmed via `window.innerWidth` in `javascript_tool`) if the window is maximized. Restore it first with a Win32 `ShowWindow(hwnd, 9)` (`SW_RESTORE`) — or just `MoveWindow` directly, which also un-maximizes — before `resize_window`/further automation, when testing a responsive breakpoint that needs a real narrow viewport.
- **Request cancellation (fixed in Phase 3)**: `runGeneration()`/`runRawGeneration()` in `App.tsx` now use an `AbortController` stored in `abortControllerRef`, and there's a Cancel button in the status bar while `loading`. `runCommand()` also refuses to start a new command while one is already in flight. If you still see two generations racing, check that both call sites are going through these helpers rather than calling `provider.generate()` directly.
- **The `keyring` crate needs an explicit backend feature or it silently no-ops.** `keyring = "3"` with no `features` compiles fine and every call *succeeds* (`set_password` returns `Ok`), but it's using the crate's internal mock/no-op store — nothing is ever written to the real OS credential store, and a `get_password` right after a `set_password` in the same process returns `NoEntry`. `Cargo.toml` must specify `features = ["windows-native", "apple-native", "linux-native-sync-persistent"]` (or the subset you actually ship for). If keychain behavior ever looks like "writes succeed but reads never find anything," check this first — it's silent, not an error.
- **SendKeys + Windows text-suggestion popups**: if automating this app's UI, a hardware-keyboard predictive-text overlay can steal keystrokes mid-string (observed dropping `[`/`]` characters while typing a Lonelog tag). Not an app bug — verify with a screenshot before concluding the editor/highlighting is wrong.
- **Clipboard-based devtools automation is dangerous — prefer SendKeys typing, or better, avoid the GUI entirely.** Pasting a JS snippet into the devtools console via `Set-Clipboard` + Ctrl+V has a real failure mode: if the `Set-Clipboard` call is part of a tool invocation that gets rejected/interrupted before running, the paste silently uses whatever was *already* on the user's clipboard instead — which once was a real Anthropic API key, briefly exposed on-screen and in a screenshot. If you must type into devtools, escape and use `SendKeys` directly (regex `([+^%~(){}])` → `{$1}` handles Windows SendKeys escaping) rather than clipboard paste.
- **Prefer a throwaway Rust example over GUI screenshots for backend-only verification.** The keyring bug above was found and fixed almost entirely via `cargo run --example <name>` (create a temp file under `app/src-tauri/examples/`, run it, delete it) — no screenshots, no window-focus juggling, orders of magnitude cheaper than driving the live app for something that doesn't actually touch the UI. Reserve live `tauri dev` + screenshot verification for things that can *only* be observed in the running webview (rendering, layout, actual click flows).
- **Window-focus is genuinely unreliable when the user is also active on the machine** — VS Code, browser tabs, etc. can steal foreground focus between one PowerShell tool call and the next (they're separate processes; nothing holds focus for you in between). Always re-find-and-focus the target window and verify `GetForegroundWindow()` immediately before sending input, ideally in the same script as the input itself, and abort that step (don't click blind) if the check fails.
- **VS Code (as the parent process hosting the automation terminal) reliably reclaims foreground *between separate tool calls*, even with no other user activity at all.** Seen twice in Phase 8: a `SetForegroundWindow`+click done atomically in one PowerShell script landed correctly every time; a `SetForegroundWindow` in one script followed by a screenshot in a *separate* script call captured VS Code instead, because focus had already reverted by the time the second script started — nothing user-driven required, just the normal handoff back to the terminal's owning window between invocations. Before concluding "the user is interfering" from a focus-mismatch, check whether the evidence is actually fresh (e.g. does the on-screen state differ between observations, or is it byte-for-byte identical — identical strongly suggests stale buffer state, not live interference). **Fix: always combine focus-check + action + screenshot into one script**, never split them across separate tool invocations when driving this app's GUI.
- **Other apps can genuinely hold foreground too, not just VS Code — identify the window, don't just retry blindly.** Phase 10 hit a persistent focus mismatch that turned out to be Microsoft Teams (an active chat), not VS Code. Use `GetWindowText`/`GetWindowThreadProcessId` on the current foreground `HWND` to name what's actually holding it (watch out: PowerShell's `$pid` is a reserved read-only automatic variable — name the local variable something else, e.g. `$procId`). If it's a real app the user is actively using (confirmed either by a changing diff snapshot, as with `features.md`, or just by what the window plainly is, like a chat app), stop and wait — don't keep retrying `SetForegroundWindow` against it.
- **`cargo` can be missing from `PATH` in a given terminal session even after a working install** (seen in Phase 5, in both the Bash/Git-Bash tool and PowerShell tool). `npm run tauri dev`/`cargo build` fail with `program not found` even though earlier phases confirmed the toolchain works. Check `Get-Command cargo`/`which cargo` before assuming the toolchain regressed — it's a session/shell-init issue, not a project state change. If it's genuinely missing, a live GUI verification pass isn't possible until it's resolved; say so explicitly rather than skipping the check silently.
- **It's fine to skip live GUI verification entirely when a change reuses an already-proven pattern closely.** Phase 4 shipped without a single `tauri dev` screenshot — every sub-feature either wired existing, already-verified logic (`listModels()`, `importSourceFile`'s copy-with-collision-avoidance pattern) into new UI, or was simple enough to desk-check by hand (e.g. tracing `compileFrontmatter()`'s output against the exact `lonelog.md` example line-by-line). Reserve live GUI passes for genuinely new interaction logic, not every touched file.
- **`app/src-tauri/Cargo.toml`'s `edition` field must be a real Cargo edition (`2015`/`2018`/`2021`/`2024`).** It briefly held `"2026"` (an accidental typo from early scaffolding customization) which made `cargo metadata`/`tauri dev` fail outright with a manifest parse error — silent until someone actually ran `tauri dev`, since `tsc`/`vite build`/`cargo check` don't touch this. If `tauri dev` fails immediately with "failed to parse manifest" / "failed to parse the `edition` key," check this field first.
- **If a `tauri dev` session from an earlier phase was left running in the background, its file watcher will pick up edits to `Cargo.toml`/`Cargo.lock` (or any `src-tauri` file) and rebuild automatically** — seen in Phase 9, where editing `Cargo.toml`'s version bumped `Cargo.lock` to match *before* any explicit `cargo check` was run in the current turn. If a Rust manifest file shows changes you didn't make yet, check `tasklist` for a leftover `Sybyl.exe`/`cargo.exe` before assuming something is wrong — it's very likely a stale watcher from a prior phase's session finishing its own rebuild, not file corruption or a merge conflict.
